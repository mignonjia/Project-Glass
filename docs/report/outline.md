**One-line thesis:** real-time world models need long-term memory. Memory has to be stored as **KV** (latents are not enough), and reading it under content-based sparse attention is a bandwidth problem that PCIe cannot serve.

## Part 1: algorithm (why store KV)

### Slide 1. Memory matters, and the community stores full KV: WorldKV
- **Figure:** `motiv_worldkv.png`
- **WorldKV** (LingBot-World-Fast 14B, training-free) keeps the full KV bank and retrieves it by camera pose.
  - Quality: PSNR 15.66 and FID 75.6. This matches full KV (15.90 / 85.7) and is far above a sliding window (12.18 / 144).
  - Speed: 4.78 fps, near the window's 5.05 fps; full KV runs at 2.36 fps.
- WorldPlay-8B, which recomputes memory from frames, sits in between (14.56 / 113). It is a different model, so this is not a clean comparison.

### Slide 2. OmniMem: full-resolution KV offloaded to host, sparse per-head retrieval
- **Figure:** `motiv_omnimem.png`
- **Design:** OmniMem (Wan2.1-1.3B + Self-Forcing) keeps "the full-resolution KV cache … per-head, chunk-level". Offloaded blocks "live in pinned host memory and are reloaded through PCIe"; the GPU keeps only 7 chunks (LRU).
- **Quality:** Dynamic Degree 82.3 vs ≈54 for the best baseline, at similar VRAM.
- **Selection must be per head:** sharing it across heads drops CLIP from 26.53 to 23.64.
- **More budget is better:** top-K = 12 gives 27.44.
- **The paper names the systems problem itself:** the selection "union explosion" means "sparse in computation, [but] a large KV memory footprint".

### Slide 3. Our test: stored KV vs latents + recompute
- **Figures:** `kv_vs_latent_quality.png` (main), `kv_vs_latent_frames.png` (visual)
- **Setup:** WorldKV code, LingBot-World-Fast 14B, 361 frames (22.5 s). The camera turns 0→90→0° three times with no translation. Every config has the same 27-latent-frame budget, except full KV.
- **Metric:** compare each frame with its first visit at the same angle, and look only at frames whose first visit has left the window.
  - The same view comes back every ~4 s, so this measures **drift from the original scene** over repeated looks. It does not test a long absence; that needs a turn-away trajectory (next step).
- **Result** (PSNR, 2 seeds):

  | Config | PSNR |
  |---|---:|
  | Stored KV + retrieval | **16.1** |
  | Full KV | 15.5 |
  | Recompute the same 18 frames from latents | 12.5 |
  | Recompute + first chunk | 11.4 |
  | Sliding window | 11.8 |

  **Recomputed memory is no better than having no memory.**
- **Visual example** (15 s apart, same 40° view): stored KV and full KV redraw the barn; window and recompute invent a different scene.

### Slide 4. Why recompute fails
- **Figures:** `kv_vs_latent_curve.png`, `recompute_v_cosine.png`
- **The gap opens exactly when the reference leaves the window.** Inside the window all configs are equal (≈17 dB).
- **Recomputed V vs stored V:**
  - Layer 0 is identical (cos 1.000), so the inputs match.
  - Deeper layers drift to ≈0.70–0.79.
  - The KV carries the context it was generated with, and latents alone cannot rebuild it.
  - Rebuilding exactly would need recursive recompute of the whole history.
- **Speed agrees:** on 14B SP8, recomputing 8 memory frames costs +283 ms per chunk vs 46 ms to fetch the stored KV from host DRAM (slide 6).

## Part 2: systems (what storing KV costs)

### Slide 5. Profiling setup
- **Model:** LingBot-World v2 14B causal-fast (Wan2.2-14B), 40 layers × 40 heads, head_dim 128, bf16.
- **Video:** 512×768, 16 fps; 1 chunk = 4 latent frames = 1 s = real-time budget; 4 denoising steps + 1 commit per chunk.
- **Parallelism:** Ulysses SP8 on 8×H200, 5 heads per GPU; FlashAttention 4 (dense and block-sparse).
- **History:** full KV, up to 120 s. That is 0.157 GB per latent frame per GPU, 75.5 GB per GPU at 120 s, and ≈3 TB per stream at 10 min.
- **Sparse attention:** 128×128 blocks, selected per layer, head and query block:
  - **VSA-style:** last 12 latent frames dense, plus the top 5% of older blocks;
  - **Light Forcing-style:** pick frames first, then blocks.
- **Quality runs:** LingBot-World-Fast v1 14B, SP4, 361 frames, 2 seeds.

### Slide 6. Workload and time per chunk
- **Figures:** `sp_sparse_workload.png`, `memory_time.png`
- **Dense full history** is compute-bound: 2646 ms per chunk at 60 s.
- **Block-sparse:** 958 ms per chunk. The attention kernel takes 38 ms and stays flat as history grows, but the KV store keeps growing linearly.
- **Bringing 20 memory frames into attention** (`memory_time.png`, M = 20 only). Fixed work per chunk is ~1,016 ms (linear layers, window attention, all-to-all); extra time on top of it:
  - stored KV in HBM: fetch +18 ms (2%);
  - stored KV in host DRAM: fetch 109 + write-back 28 = +137 ms (13%);
  - recompute from latents: +757 ms (75%).
- **Open item:** the host-DRAM run also slows the rest of the chunk by ~330 ms; cause not yet explained (noted on the figure, not drawn).
- Figure script: `plot_memory_m20.py` (local; the original `plot_report.py` on the server still draws the M = 8 / 20 version with gray bars).

### Slide 7. Access pattern: which older KV blocks are read
- **Figures:** `access_pattern.png` (VSA-style only, redrawn larger by `plot_access_pattern.py` from curves digitized out of the original SVG), `attn_trace_reuse_rate.png` (Tianqi)
- "Older" = KV blocks beyond the 12 most recent latent frames; all three are per layer and head, averaged.
  - **(a) Read per forward ≈40%:** blocks picked by the 48 query blocks in one forward ÷ all older blocks (PAN 21.8%).
  - **(b) New between forwards ≈7%:** share of a forward's blocks the previous forward did not read (PAN 6.7%).
  - **(c) Shared with the previous chunk ≈70–74%:** share of this chunk's blocks the previous chunk also read (PAN 65%).
- They set the fetch bandwidth: re-read every forward (a), fetch once per chunk (a + b), keep the previous chunk's blocks (a + b + c).
- **Reuse (Tianqi):** each fetched block is used by ≈6 query blocks. The rate is stable over time and steps, with per-layer bands.
- **Arithmetic intensity:**
  - without merging: AI = 128 FLOP/B;
  - merging requests within a forward: ≈770;
  - caching across the 5 forwards: ≈3300;
  - in bandwidth terms: 5 → 0.85 → 0.2 TB/s at 650 TFLOP/s.

### Slide 8. Fetch cost: PCIe cannot keep up
- **Figures:** `fetch_bw.png`, `bw_demand.png`
- **Host→GPU bandwidth:** 28 GB/s per GPU for large copies, but only 4.8 GB/s for one head's 128-token K or V. OmniMem's ~15 KB blocks would be even worse.
- **VSA-style demand per GPU**, measured to 117 s and extrapolated to 10 min:

  | Strategy | 117 s | 10 min |
  |---|---:|---:|
  | Re-read every forward | 139 GB/s | ≈720 GB/s |
  | Fetch once per chunk | 32 GB/s | ≈170 GB/s |
  | Keep the previous chunk's blocks | 9 GB/s | ≈41 GB/s |

  All three exceed PCIe within minutes.
- **This is the Glass regime:** TB-scale capacity, 0.04–0.7 TB/s per GPU, fine-grained, and decided at run time.

### Slide 9. Caveats and next steps
- **Caveats:**
  - Quality: one scene, one 22.5 s trajectory, 2 seeds.
  - Our recompute is training-free. A model trained to use recomputed memory, like WorldPlay, might do better.
  - LingBot was not trained with sparse attention. The access pattern matches PAN's, but quality under sparse attention is unverified.
  - VSA-style selects a fixed ratio, so compute grows with history; a fixed top-k would cap it.
- **Next steps** (need GPUs):
  - more scenes and seeds;
  - explain the host-DRAM M = 20 overhead;
  - clean VSA timing;
  - fixed-k trace;
  - end-to-end sparse fetch from a capacity tier.
