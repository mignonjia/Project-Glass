# 固定预算稀疏 + 复用度 R 的估算（转圈游戏场景）

> 2026-10-08。全部为 **[估]**，模型参数取自 `pan_compute_comm_estimate.md` 与 `david_training_load.md`。
> 问题：如果每个 query 只看固定数量的远端历史（固定预算），且复用度低，PAN 的 DF + VSA 训练会不会变成带宽瓶颈？

## 场景

- PAN，720p、24 fps：1 个 chunk = 0.67 s = 3776 token（补齐 4096 行 = 32 个 tile）。
- 游戏里**转圈走，周期 30 s**：每个 chunk 要找的历史在 30 s 前，也就是 45 个 chunk 之前（更早的圈也有同一处）。
- 稀疏：最近 3 个 chunk 精确 + 每个 query tile 再选 **k 个远端 tile**（固定预算，不随长度增长）。默认 k = 32，即每个 query tile 看 4096 个远端 token，正好一个 chunk 的量。
- 硬件：GB300 2.5 PFLOP/s × 45%；每卡单向带宽 NVLink 0.9 TB/s、IB 0.05 TB/s、Glass 4 TB/s。

## 复用度 R 的定义

**R = 一个被取来的远端 tile，被本卡上多少个 query tile 用到。**

每个 chunk 要取的不重复 tile 数 = 32 × k / R。R 越大，每取 1 字节能做的计算越多，越偏算力。

## 每个 chunk、每层的计算（32 个 head 合计，k = 32）

| 部分 | 公式 | FLOPs |
|---|---|---:|
| 线性层 | 3776 token × 0.6525 GFLOP | 2.46 T |
| 窗口 attention | 4 × 4096 × (3 × 4096) × 4096 | 0.82 T |
| 远端 attention | 4 × 4096 × (k × 128) × 4096 | 0.27 T |
| 合计 | | 3.55 T → **3.17 ms** |

每取一个 tile（K + V，32 个 head）= 2 MiB。一个 chunk 的完整 KV = 32 tile = 67 MB。

## 结果：通信 / 计算（训练整步，连续放置）

训练整步 = forward + 重算 + backward，取数 3 轮、计算 4 倍，所以在 forward 的比值上 × 0.75。

| k（远端 token） | R = 1：NVLink / IB / Glass | R = 3 | R = 10 | R = 32 |
|---:|---|---|---|---|
| 8（1K） | 0.15 / 2.7 / 0.03 | 0.05 / 0.9 / 0.01 | 0.01 / 0.3 / 0.00 | 0.00 / 0.1 / 0.00 |
| 16（2K） | 0.29 / 5.3 / 0.07 | 0.10 / 1.8 / 0.02 | 0.03 / 0.5 / 0.01 | 0.01 / 0.2 / 0.00 |
| **32（4K）** | **0.56 / 10.2 / 0.13** | **0.19 / 3.4 / 0.04** | 0.06 / 1.0 / 0.01 | **0.02 / 0.3 / 0.00** |
| 64（8K） | 1.05 / 18.9 / 0.24 | 0.35 / 6.3 / 0.08 | 0.10 / 1.9 / 0.02 | 0.03 / 0.6 / 0.01 |
| 128（16K） | 1.84 / 33.0 / 0.41 | 0.61 / 11.0 / 0.14 | 0.18 / 3.3 / 0.04 | 0.06 / 1.0 / 0.01 |

表中数字是**比例**（通信时间 ÷ 计算时间），没有单位。换成绝对时间的例子（R = 3、k = 32）：
- 每个 chunk-层 forward：计算 3.17 ms；取 32 × 32 / 3 ≈ 341 个 tile ≈ 715 MB，NVLink 上 0.80 ms；比例 0.25，训练整步 × 0.75 ≈ 0.19。
- 10 分钟 720p、72 卡：每卡 550 个 chunk-层。每步计算 550 × 4 × 3.17 ms ≈ **7.0 s**；通信 NVLink ≈ **1.3 s**、IB ≈ 24 s、Glass ≈ 0.3 s。
- 计算比固定 5% 比例时的 16.5 s 少，因为固定预算下 attention 不再随长度平方增长。

条纹放置时，前 2 个 chunk 的窗口也要从别的卡取（每 chunk 多 64 个 tile）。k = 32 时：R = 32 → NVLink 0.05；R = 3 → 0.22；R = 1 → 0.60。

**NVLink 上通信超过计算的门槛**：R = 1 时 k ≥ 61（每个 query tile 约 7.8K 远端 token）；R = 3 时 k ≥ 266（约 34K）。

## 转圈场景的 R 是多少

| 情况 | R 估计 | 依据 |
|---|---:|---|
| 理想转圈：一个 chunk 的 32 个 query tile 都在找"30 s 前同一处" | **16–32** | 目标集中在 1–2 个历史 chunk（32–64 个 tile），32 × 32 次选择落在这些 tile 上 |
| 再加相邻 chunk 共享（连续放置） | 更高 | chunk t 和 t+1 的目标也相邻（t−45 和 t−44），同一卡上连续的 chunk 取的基本是同一段 |
| 预算分到多圈（t−30 s、t−60 s、t−90 s 各取一些） | 约 5–10 | 不重复的 tile 随圈数成倍增加 |
| 实测的一般游戏数据（固定比例 5%，448p） | **约 3** | trace：一个 chunk 内 14 个 query block 的选择并集 ≈ 单个的 4.5 倍 → 14 / 4.5 ≈ 3.1 |
| 最坏：每个 query tile 选的都不一样 | 1 | 上界情形 |

**R ≈ 3 的来历与修正**：
- 推算方式：448p 一个 chunk 有 14 个 query block，每个选 s 个 tile。trace 测得一个 chunk 内选择的并集 ≈ 4.5 s，所以 R = 14 s / 4.5 s ≈ 3.1。这与训练 trace 估的"每卡 1 个 chunk 时 R ≈ 3"一致。
- 但它只对应**每卡 1 个 chunk** 的放置。10 分钟、72 卡时每卡（或每个 CP 组）有 12.5–100 个 chunk，相邻 chunk 的选择大量重叠；训练 trace 估**每卡 12 个 chunk 时 R ≈ 12.5**。
- 它来自固定 5% 比例（10 s 时每个 query block 只选 4–5 个 tile），且是 448p（每 chunk 14 个 query block，720p 是 32 个）。固定预算 k = 32、720p 下 R 很可能更高。
- 三点都说明真实 R > 3，对 glass 更不利。

**端到端上限（k = 32，通信与计算不重叠）**：

| R | 对应情况 | 通信/计算（NVLink） | NVL72 → Glass |
|---:|---|---:|---:|
| 3 | 每卡 1 个 chunk | 0.19 | 1.14× |
| **12.5** | **每卡约 12 个 chunk（10 分钟、72 卡）** | **0.045** | **≈ 1.035×** |
| 16–32 | 理想转圈 | 0.02–0.04 | 1.02–1.03× |

任何互连的上限都是 1 + 通信/计算（Amdahl），所以更快的光带宽也无法明显超过这些值。

另外，连续放置时，如果一张卡上的 chunk 数超过 45（例如 Ulysses 8 × CP 9 时每个 CP 组有 100 个 chunk），转圈的目标大部分**就在本卡**，几乎不用取。

## 结论

1. **转圈场景反而是高复用（R ≈ 16–32）**：所有 query 都在找同一段过去，取一次能用很多次。NVLink 上通信只占计算的 2–4%，NVL72 内仍然是算力瓶颈。
2. **即使按每卡 1 个 chunk 的复用度（R ≈ 3），NVLink 上也只有约 0.2；按 72 卡的实际放置（R ≈ 12.5）只有约 0.045，端到端收益约 3–5%**。要让 NVLink 成为瓶颈，需要 R ≈ 1 且每个 query tile 取 7.8K 以上的远端 token，也就是"每个区域都要从不同时间、不同地方的历史里各取一大块"，比转圈分散得多。
3. **根本原因在 dense 29B 的线性层**：一个 chunk-层的线性计算 2.46 TFLOP，对应一个 chunk 的 KV 只有 67 MB，相当于每字节 3.7 万 FLOP；而 NVLink 的平衡点约是每字节 1250 FLOP。每个 chunk 要从远端取大约 30 个 chunk 的不重复 KV，通信才追得上计算。
4. **在普通集群（IB）上不一样**：R ≈ 3 时通信是计算的 3–4 倍，R ≈ 16–32 时约 0.3–0.6。glass（或任何 NVLink 级的域）相对 IB 集群有明显收益，但相对 NVL72 没有。
5. **能改变结论的是降低每 token 的线性计算**，例如 MoE（激活参数约 3B，线性层计算约降一个数量级）。此时门槛会显著降低，需要用同样的方法单独估算。

## 具体配置：10 分钟、720p、每个样本 16 卡（k = 32）

每卡每步计算 = 900 chunk × 44 层 × 4 × 3.55 TFLOP ÷ 16 ÷ 1.125 PFLOP/s ≈ **31.4 s**。

| 切法 | 每卡每步通信 | NVL72 通信（÷ 计算） | Glass 通信（÷ 计算） | 每步（不重叠）NVL72 / Glass | 加速上限 |
|---|---:|---:|---:|---:|---:|
| **Ulysses 16**（按 head 切，每卡有完整序列的 2 个 head，**检索全在本地**） | 1.08 TB | 1.20 s（0.038） | 0.27 s（0.009） | 32.6 / 31.6 s | **1.03×** |
| CP 16 连续，R = 12.5 | 1.51 TB | 1.68 s（0.054） | 0.38 s（0.012） | 33.0 / 31.7 s | 1.04× |
| CP 16 连续，R = 3（悲观） | 5.55 TB | 6.17 s（0.197） | 1.39 s（0.044） | 37.5 / 32.7 s | 1.15× |

- 通信组成：Ulysses 16 = Q/K/V/O 的 all-to-all（3 轮）0.86 TB + FSDP 0.22 TB；CP = 取远端 K/V（3 轮）+ 窗口边界 + FSDP。
- CP 16 拆解（每卡 56 个 chunk，2475 个 chunk-层）：每 chunk-层取 32 × 32 / R 个 tile × 2 MiB，× 3 轮。R = 12.5 → 1.28 TB；R = 3 → 5.32 TB。窗口边界 2 个 chunk × 67 MB × 44 层 × 3 ≈ 18 GB。表中未计压缩分支收集全部历史 block 均值的流量，约 0.47 GB / 层 × 15/16 × 44 × 3 ≈ 58 GB（+0.06 s）。每卡 56 个 chunk 时 R 很可能高于 12.5，所以 R = 12.5 一行偏保守。
- **16 卡 ≤ 32 个 head，所以 Ulysses 16 可行且最优**：每卡持有整段序列的 2 个 head，top-k 检索不需要跨卡取 K/V。只有卡数超过 head 数，或单卡放不下整段序列的 attention 时，才需要 CP。
- 显存（只算线性部分）：激活 ≈ 765 KB/token × 340 万 ÷ 16 ≈ 162 GB + 模型状态 22 GB + 其他约 20 GB ≈ **204 GB < 288 GB**，GB300 放得下，用不到 glass DRAM。
- 吞吐：NVL72 放 4 个样本（64 卡，8 卡空闲）；GlassML 面板 64 个 tile 也是 4 个样本。

### 预算加大到 k = 320（每个 query tile 约 4 万远端 token）

| | k = 32 | k = 320 |
|---|---:|---:|
| 每 chunk-层 FLOPs（线性 / 窗口 / 远端） | 3.56 T（69% / 23% / 8%） | 6.04 T（41% / 14% / 46%） |
| 每卡每步计算 | 31.4 s | **53.1 s**（线性 21.7 + 窗口 7.3 + 远端 24.2） |
| Ulysses 16：通信 / 加速上限 | 1.08 TB，3.8% / 1.03× | 1.08 TB（不随 k 变），2.3% / **1.02×** |
| CP 16，最慢卡：通信 / 加速上限 | 1.57 TB（R = 12.5），6% / 1.04× | **7.8 TB**，16% / **1.12×** |

- k = 320 时，CP 的取数在 R = 12.5 和 R = 3 下都触到上限"取回全部更早历史"（和 dense 一样）。连续切时最后一张卡要取前面 15 张卡的全部 K/V，所以最慢卡约 7.8 TB，平均约 4.0 TB。
- 上一节 k = 32、R = 3 的 CP 一行也部分触到这个上限（平均 3.7 TB，最慢卡 5.6 TB）。
- 结论：加大预算让 attention 计算和取数一起涨；Ulysses 下取数不涨，所以更偏算力；CP 下最多涨到"dense 取数"，NVL72 上约 16%。

## 局限

- R 是按场景推理出来的，不是转圈数据的实测。要实测，需要录一段转圈的游戏视频跑 trace。
- 忽略了压缩分支（全部历史 block 均值）的计算和收集：计算可以忽略，收集量约每层几十 MB。
- 没有建模计算与通信的重叠；× 0.75 的训练系数沿用 `david_training_load.md`。
- 线性层 FLOPs / token 由文档反推（30.8 TFLOP / 4.72 万 token / 层）。

## 计算脚本

```python
FLOPS = 2.5e15 * 0.45
BW = {"NVLink": 0.9e12, "IB": 0.05e12, "Glass": 4e12}
ROWS, TOK, D, TILES = 4096, 3776, 4096, 32
LIN = TOK * 0.6525e9                 # 线性层 / chunk-层
WIN = 4 * ROWS * (3 * ROWS) * D      # 窗口 3 个 chunk
TILE_BYTES = 32 * 64 * 1024          # 一个 tile，K+V，32 个 head

def ratio(k, R, halo_tiles, bw):
    rem = 4 * ROWS * (k * 128) * D
    comp = (LIN + WIN + rem) / FLOPS
    uniq = TILES * k / R + halo_tiles
    return uniq * TILE_BYTES / bw / comp * 0.75
```
